# 交互与实现细节

这份文档写给**要改这个项目的人**。README 回答"这是什么、为什么用它"，
这里回答"它到底是怎么动起来的"。

---

## 一、卡片是"丢"出去的

拖拽不是把一个矩形从 A 移到 B，是一个**真正的刚体积分器**，手写的半隐式欧拉。

只有**一个刚体、零碰撞、一根弹簧**。物理引擎 90% 的能力（broadphase、约束求解器、
休眠、复合体、CCD）在这里一个都用不上，而最小的 2D 引擎 Matter.js 也要 80 KB 加一份
许可证声明。真正让拖拽有物理感的是四件事：

1. **两个轴都动。** 指针是**目标**，不是位置，所以卡片会滞后于手指 ——
   "它自己滚走"的感觉就是从这里来的。早期版本把卡片 1:1 焊死在光标上，那只是在移动一个矩形。
2. **拖拽用一阶跟随，不是弹簧。** 弹簧天然欠阻尼：拖到一半突然停手，卡片会在原地弹一下。
   而**抓在手里的东西不会自己弹**。指数逼近给出同样的滞后感，但每一步只走完剩余距离的
   固定比例，数学上不可能过冲。
3. **松手才是弹道。** 速度取自**指针**而不是卡片，所以方向是二维的：斜着甩就斜着飞，
   角速度随甩出方向自旋。没过判定线则由同一套积分器滑回中位。
4. **每个常数都写成"每 16.7 ms"再按实际耗时取幂**，所以 144 Hz 和 30 Hz 手感一致。

```js
const P_FOLLOW = 0.34;   // 每步走完剩余距离的比例（一阶跟随）
const P_AIR    = 0.992;  // 抛出后的空气阻尼，几乎为零
const P_SPIN   = 0.055;  // 每单位水平速度带来的自旋
```

**决定的方向仍然只有左右。** 你可以把卡片往任意方向丢，但只有水平分量构成「过 / 不过」，
蒙版和标签也只跟水平位移走。

## 二、卡片自己带 CSS 过渡，这件事踩过三次

`.photoCard` 上有 `transition: transform`。只要它和手写 transform 同时存在，就会出问题：

| 症状 | 原因 |
|---|---|
| 卡片**完全拖不动** | `cardRise` 的 `animation-fill-mode: both` 永久覆盖了内联 transform |
| 松手后卡片**从屏幕外滑回中间** | `physReset()` 清空内联 transform 时触发了过渡 |
| 运动被**抹成糖浆** | 物理每帧写 transform，每次都重启那条过渡 |

**结论：谁在写 transform，谁就必须先把过渡关掉，改完强制重排，再恢复。**

```js
el.photoCard.style.transition = 'none';
el.photoCard.style.transform = '';
void el.photoCard.offsetWidth;      // 让"无过渡"这一状态真正生效
el.photoCard.style.transition = '';
```

## 三、不要给同一张照片准备两个元素

曾经为了让"下一张"看起来是叠在下面的，有一个 `.stackPeek` 层。它按**当前照片的尺寸**布局，
所以只要两张照片的宽高比不同，peek 就必须改尺寸 —— 而 `width/height` 是瞬间生效的，
`--pk-x/--pk-y` 却走 430 ms 过渡，于是**先跳尺寸、再滑位置**，看起来就是一次抽动。

竖版换竖版时尺寸几乎不变，所以只有部分翻页会出问题 —— 这解释了为什么它一直很难复现。

**根因不是"没同步好"，是"有两个东西需要同步"。** 删掉之后，整个类别的 bug 一起消失了。

## 四、出卡和入卡是同时的

这是早期最不连贯的地方：**出卡飞完了，下一张才开始上浮**，中间隔着一整个动画时长。

修法是让离场和入场重叠：`.lifting` 类在出卡开始的那一刻就加上，入场动画不等离场结束。

> **踩坑**：`.stackPeek` 是 `.photoStage` 的**兄弟节点**（都在 `#cardWrap` 里），
> 所以 `.photoStage.lifting .stackPeek` 这条选择器永远匹配不上。规则确实在
> `document.styleSheets` 里，computed value 就是不变。要挂在 `.cardArea` 上。

## 五、决定之后，下一张要无缝接上

有三个卡顿，都是"等网络"造成的：

1. **`commitDecision` 曾经 await `/api/decide` 再 render。** 实测往返中位数 3.7 ms，
   但最差 196.7 ms —— 这段时间舞台是空的。改成**乐观渲染 + 后台保存**。
2. **`fitStage()` 曾经依赖 `el.photo.naturalWidth`。** 新卡片会沿用上一张的框约 250 ms，
   然后**在动画途中**被重新设置尺寸。30 对相邻照片里有 4 对宽高比差异超过 0.02，
   每一对都是一次可见的跳动。改成优先用照片自带的 `width/height`，并在加 `.entering` **之前**布局。
3. **预览图是 71–244 KB，冷启动 250–470 ms，命中缓存 3 ms。** 所以提前预取后面两张。

## 六、人脸：一次推理拿到全部信息

MediaPipe **Tasks API**（`mediapipe 1.1.0` 已经没有 `mp.solutions` 了）：

```python
FaceLandmarker(..., output_face_blendshapes=True)
```

一次推理同时得到：

- **478 个面部关键点**（含**虹膜**，索引 468–477）
- **52 个 ARKit 风格 blendshape**（`eyeBlinkLeft`、`browDown`、`eyeLookOutLeft`…）
- 头部姿态矩阵

### ⚠️ blendshape 是神经网络的回归输出，不是测量值

它带有**系统性的单侧偏差**。实测：同一个人的四张照片，一只眼 0.44–0.49、另一只 0.19–0.33，
阈值 0.40 —— 四张全被判"眼睛可能闭着"。**但真正的眨眼是双眼同时闭合的。**

### 已经修掉的三条（对应 `ANALYSIS_VERSION = 4`）

| 问题 | 修法 | 实测 |
|---|---|---|
| **单眼证据当成双侧结论**。上面那四张全是"一只眼高、另一只低"，全被判成眨眼 | **要求双眼同时过阈值**。阈值本身没动 —— 双侧要求就是全部所需，再降阈值只会把噪声放回来 | 4 张误报 → **0** |
| `CATCHLIGHT_MIN = 0.12` **几乎正好压在中位数 0.112 上**，等于在说"低于平均水平就算缺" | 压到 **0.04**，只回答标签真正声称的问题：**到底有没有高光** | 6 张 → **0** |
| `browDown > 0.40` 的标签写"表情严肃" —— **在模型没说的话上加戏** | 阈值抬到 **0.55**（只有明显压低才触发），标签改成 **「眉头压低」**，只说测到的东西 | 1 张 → **0** |

修完之后这个库上剩 **7 种**问题，而决策数一个没变（`keep 76 / mark 8 / reject 9`）——
说明改的是**误报**，不是把真问题一起抹掉了。

**还没做的两条**（都是升级，不是修 bug）：

| 现在 | 应该改成 |
|---|---|
| `eyeBlink` blendshape | **EAR**（Eye Aspect Ratio：上下眼睑距离 ÷ 眼睛宽度）。真眨眼 EAR 掉约 40%，而且是**几何测量**，数值可直接解释 |

### ⚠️ 人脸检测漏掉大半：**是喂给模型的方式错了，不是模型不行**

实测一个 93 张的旅行库：**只有 18 张（19%）检出人脸**。前 20 张里只有 4 张。
界面上表现为「每张都说没检测到脸」—— 用户合理地以为功能坏了。

**排查过程（每一步都实测）：**

| 试了什么 | 结果 |
|---|---|
| 降低检测置信度 0.35 → 0.03（默认是 0.5） | 仍然 0 张 |
| 提高分辨率 1500 → 3000 → **原始 6000px** | 5 / 4 / 4 张 —— **更高反而更少** |

**"更多分辨率反而更差"这一条是线索。** 它只可能意味着一件事：**检测器内部会把输入
统一缩放到固定尺寸**（BlazeFace 约 256×256）。喂 6000px 进去只是被缩得更狠，
**脸在检测器眼里永远一样小**。

**验证方法：把脸所在的区域裁出来单独喂。**

| 照片 | 整图 1500px | 裁出上半身 | 裁出头部附近 |
|---|---|---|---|
| DSC09891 | 0 | **1** | **1** |
| DSC09892 | 0 | **1** | **1** |
| DSC09893 | 0 | **1** | **1** |
| DSC09869 | 0 | **1** | **1** |
| DSC09856 | 0 | 0 | 0 |

前四张是**站着的人、脸没被挡、也没旋转、全身照** —— 裁出来立刻就找到了。
`DSC09856` 裁了也找不到，那张**确实**被手和筷子挡住了（这张是模型的真实极限）。

**结论：问题是"脸在画面里占比太小"，不是"脸太难"。**

### 修法：分块二次检测（已实施，`ANALYSIS_VERSION = 5`）

整图找不到脸时，把画面切成 5 块重叠区域（四个角 + 中央），逐块检测。
**关键在于坐标映射：** 裁切返回的关键点在裁切图坐标系里，必须映射回整图，
否则下游全部错位。`_detect_tiled()` 返回 `(res, sx, sy, ox, oy)`，关键点解包时应用它：

```python
pts = np.array([[p.x * sx + ox, p.y * sy + oy, p.z] for p in lms])
```

头部姿态的**欧拉角是旋转量，平移不影响**；blendshape 是纯形状量 —— 所以这两样
不需要任何处理，平移只影响框和位置。

**只有整图找不到时才触发**，所以大脸的照片一分钱不花。

**实测（93 张旅行照，同一台机器）：**

| | 改前 | 改后 |
|---|---|---|
| 检出人脸的照片 | **18 张（19%）** | **73 张（78%）** |
| 人脸总数 | 19 | **77** |
| 分析总耗时 | 6–8 秒 | **10 秒** |

**端到端确认**（真实浏览器、真实按键，见下面的方法一节）：
`DSC09867`（人**躺着**，旋转 90°）改前 0 张脸，改后 **1 张**，
`#overlay` 画出 3 个矩形（脸框 + 两只眼睛），提示文字「这张检出 1 张脸」。

**仍然找不到的**：`DSC09856` —— 手和筷子真的挡在脸中间。裁切也找不到。
这是模型的真实极限，不是喂法的问题。

> **教训**：上一轮我只测了一张照片（恰好是那张真被遮挡的），就写下"这是模型的固有局限"。
> **一个样本撑不起一个结论。** 测完整个库才发现是 19%，而不是"偶发漏检"。
> 而且"更多分辨率反而更差"这条反直觉的数据，才是真正的线索 ——
> 它指向"检测器内部会重缩放"，而不是"照片太难"。

复现脚本：
- `evaluation/face_miss.py` —— 逐关卡报告为什么某张脸被丢掉
- `evaluation/face_resolution.py` —— 三种分辨率下的检出数
- `evaluation/face_crop.py` —— **决定性的那个**：裁切 vs 整图

### 遮挡的脸，检测器确实看不见

实测 DSC09856.JPG：一个人端着筷子，**眼睛和眼镜都清晰可见**，但一只手挡在脸中间。
MediaPipe 报 **0 张脸**。把检测置信度从 0.35 一路降到 **0.03**（默认是 0.5）—— **仍然是 0**。

这是 BlazeFace 这类短程检测器的固有局限：它依赖完整正脸的特征，**遮挡会让它整体失败**，
而不是给出一个低置信度的框。

**后果要说清楚：**「有人脸」这个筛选会**漏**，所有基于人脸的检查（闭眼、表情、视线）
在这些照片上**整个不参与**。不是判错，是根本没跑。

**界面上不许替照片下结论。** 第一版提示写的是「这张没检出人脸」——
那是在断言照片里没有人脸，而这张照片里明明有。现在写的是：

> 人脸框：这张没检测到脸 —— 被遮挡、侧脸或太小时会漏

**说的是软件做了什么，不是照片里有什么。**

> 要真正解决，得换一个对遮挡更鲁棒的检测器，或者加一路用关键点回归兜底的二次检测。
> 那是**换模型**，不是调参数 —— 上面那五个置信度已经证明了这一点。
> 复现脚本：evaluation/face_miss.py。

### 视线：试过用虹膜关键点，**结论是不换**

MediaPipe 的 478 点里已经带了虹膜（468 / 473 是虹膜中心，469–472 / 474–477 是周围的环），
而代码一直在用 8 个 `eyeLook*` 回归输出。看起来是个白捡的升级，所以先做了对拍，
**没有直接替换**。结果如下。

**① 几何量在图像坐标里，分不清"转头"和"转眼"。** blendshape 天然是头相对量，
而在图像上量虹膜位置，头一转眼睛整体就平移 —— 对抓拍人像来说这是致命的。
要修得把关键点用头部姿态矩阵转回标准脸坐标系，那是另一个量级的改动。

**② 真正的障碍是分辨率：**

```
分析分辨率 ANALYSIS_EDGE = 1500px
眼睛宽        中位 47.6px
虹膜直径      中位 21.3px
```

虹膜中心**一个像素**的误差 = 归一化单位里的 **0.042**，而真实视线偏移是 0.2–0.4。
**噪声占信号的一到两成。** 要让它可靠，分析分辨率得翻两三倍，分析时间按面积涨 ——
6–8 秒会变成一分钟以上。**不值得。**

**③ 而现在的实现并没有坏。** 被标记的 3 张 `gaze_away` 是 0.71–0.74，阈值 0.45，
都是远离阈值的**高置信度**判断。

> **对拍脚本保留了**：`evaluation/gaze_compare.py`（新旧指标同脸对比 + 与 yaw 的相关性）、
> `evaluation/iris_probe.py`（验证 468/473 到底是不是虹膜中心）、
> `evaluation/eye_pixels.py`（量实际像素尺寸）。
> **如果以后把分析分辨率提上去，先跑第一个脚本，用数据决定换不换。**

**教训**：这一条差一点变成"看起来更先进所以换掉"。**多测量一次，省下了一个更慢、更抖、
更难解释的实现。** 而且真正拦住它的不是公式，是**眼睛只有 48 像素宽**这件事 ——
那是管线问题，不是算法问题。

## 七、阈值必须相对，不能绝对

一个绝对分数跨相机、跨场景、跨题材不可比：雪山天生就亮会被判过曝，
大光圈人像的背景天生就糊会被判模糊。所以：

- **模糊**：按相机机型自动标定，且必须同时低于本次会话中位数的一定比例
- **曝光**：绝对下限 **+** 本次会话分位数双条件
- **相似照片**：只在同一次拍摄内部比较（同相机、同镜头、同光线，干扰变量自动抵消）
- **看别处**：会话相对 + 只作提示，**从不驱动「不过」**（抓拍时看别处是常态，不是缺陷）

代价是**分析必须两趟**：第一趟出原始信号，第二趟做库内标定和分组。

## 八、性能

93 张 Sony ILCE-7C 24 MP JPEG，**6–8 秒**分析完（多进程）。

几个关键决定：

- `ANALYSIS_EDGE = 1500` —— 分析用降采样图，不是原图
- 缩略图分级：`THUMB_SMALL=400`（列表）、`THUMB_CARD=1600`（预览）、`THUMB_ZOOM=3000`、`FULL_EDGE=4096`
- **`/img/<id>/full` 对浏览器原生支持的格式直接给原文件**，不重新编码。本地优先：没有带宽要省，
  而 1600px 的预览放大到 400% 就是一张糊照片
- RAW / HEIC 必须转码一次，`full` 给出能取到的最大预览

## 九、开发时的坑

- **不要用 `getAnimations()` 验证动画**：在非合成标签页里它返回 0，过渡会冻在起始值。
  用 **MutationObserver**，或者关掉过渡直接读目标值。
- **`setTimeout` 会被节流到约 1 秒**，`requestAnimationFrame` 根本不触发。
  截图背景标签页会得到冻结的过渡。
- **Node 冒烟测试的 DOM 是合成的空壳，不解析 `innerHTML`** ——
  `querySelectorAll` 永远返回空。任何依赖渲染结果的断言在那边都是**假测试**。
- **rAF 需要手动泵**：`evaluation/web_smoke.js` 里有一个可控时钟和 `pump()`，
  否则物理积分器一步都不会走，所有拖拽断言都读到 0。
- **`_dev_token()` 会遍历 `guopian/`**，而 portable 模式下 catalog 和缩略图缓存
  就在 `guopian/catalogs/` 里面。每个打开的标签页每秒轮询它一两次 ——
  所以要跳过 `catalogs`，否则就是在反复列举一堆缓存文件。
- **`anim_check.py` 在浏览器不可用时返回 exit 2，不是 1。**
  "测不了"和"失败了"是两件事，混在一起会让人去修一个不存在的 bug。

### 关于"静默失效"这件事

这个项目反复栽在同一类问题上：**破坏了不会有任何报错**。

| 症状 | 真实原因 |
|---|---|
| 界面上的词对不上 | 同一组词写在四个地方，改了一处 |
| 换配色要全文件搜索 | 颜色以字面量散落在 17 处 |
| 卡片完全拖不动 | `animation-fill-mode: both` 永久覆盖内联 transform |
| 松手后从屏幕外滑回来 | 清空内联 transform 触发了 CSS 过渡 |
| 按钮样式莫名其妙变了 | 两个 `.btn` 定义，后定义的静默生效 |
| 依赖关系靠考古 | 共享工具埋在某个视图文件里，加载顺序只是注释 |

所以 `evaluation/hygiene.py` 单独守着几条**能可靠判断**的规矩。
它不追求覆盖一切 —— 一个天天误报的检查一周内就会被关掉，**比没有更糟**。
能查的查死，查不了的**在脚本注释里写明为什么不查**。

## 技术选择

| | 用了什么 | 为什么 |
|---|---|---|
| **前端** | 原生 JS + CSS，**零依赖、无构建步骤** | 一个本地工具不需要 Webpack。打开 DevTools 看到的就是源码 || **后端** | Python 3.10 + Flask，只监听 `127.0.0.1` | 生态里图像处理和人脸模型最成熟的地方 |
| **人脸** | MediaPipe Face Landmarker（Tasks API） | 一次推理拿到 478 关键点 + 52 blendshape + 头部姿态，全本机 |
| **图像** | Pillow + numpy | 够了，而且不会引入一个几百 MB 的依赖 |
| **存储** | SQLite（WAL） | 单文件、零配置、可只读打开 |

界面是深色的，这不是风格选择 —— **看照片时周围越暗越好**。
主色是中性近黑 `#0B0C0E`，不是生成器爱给的蓝调深色：有色的环境光会改变你对照片的判断。

### 前端是浏览器原生 ES module（十一个文件，零依赖、零构建）

```
web/index.html          唯一的 <script type="module" src="/home.js">
web/core.js      72 行  G（$ $$ api toast esc sleep fmtCount）+ 视图切换   无依赖
web/state.js     70 行  el / S / V / LABEL / VERDICT / OWNED / cur        无依赖
web/view.js     186 行  适应窗口、缩放、平移、滚轮与双击手势
web/physics.js  376 行  拖拽刚体积分器 + 鼠标手势 + 蒙版/印章反馈
web/histogram.js106 行  人脸框、直方图、过曝斑马纹
web/list.js     192 行  左侧照片列表 + "上次看到哪一张"的记忆
web/card.js     313 行  卡片本身：预览、原图、建议、问题标签、元信息
web/grid.js      91 行  网格视图（框选批量决定）
web/keys.js     159 行  键盘。全应用唯一一处键位表
web/app.js      609 行  接线层：生命周期、决策流程、对话框、以及所有模块的装配
web/home.js     485 行  首页：项目列表、详情、文件夹浏览器 —— 也是唯一入口
```

依赖只有一个方向，没有环：

```
core.js  state.js                      ← 叶子，谁都不 import
   ↑         ↑
 view.js ────┤
   ↑         │
physics.js   ├── histogram.js
   ↑         │
 list.js ────┘
   ↑
 card.js
   ↑
 grid.js
   ↑
 keys.js
   ↑
 app.js     ← 所有 configure() 装配都集中在这里
   ↑
 home.js    ← 入口
```

几条向上的线（列表点击要换卡片、物理甩完要落决定、键盘敲了要分发到动作、
库被关掉要回首页）不能 import 回去 —— 那就成环了。它们全部由 `app.js`
在末尾用 `configure({...})` 注入，注入的名字和接收方模块里的占位符同名，
所以被注入的函数体一个字都不用改。

`home.js` 静态 import `app.js`，这一条 import 就是**启动竞态的修法**：
原来是三个普通 `<script>`，`home.js` 末尾直接 `Home.boot()`，它
`await fetch('/api/home')` 之后调 `App.setLabels()` —— 那时 `app.js` 往往
刚解析到一半，能跑只是因为**网络往返比解析 73 KB 慢**。现在求值顺序由
import 图保证，`app.js` 不可能没跑完。

`hygiene.py` 的第 4 组会静态检查：每个 `import` 的路径存在、名字真的有对应
`export`、依赖图无环、每个 `.js` 都是模块（没人往 `window` 上挂东西）、
以及"跨模块用到的名字都 import 了"。

### 组件只有一个基类

所有按钮都是 `.btn` 加修饰符，几何形状写在基类里，修饰符只改颜色和尺寸：

```html
<button class="btn">默认</button>
<button class="btn ghost">次要</button>
<button class="btn primary">主要动作</button>
<button class="btn danger">破坏性动作</button>
<button class="btn primary block lg">整行的大按钮</button>
```

> 这里踩过一次：给主页加按钮时**又写了一个 `.btn`**（`34px` / `.pri` / `.danger`），
> 而项目里本来就有 `.btn`（`30px` / `.primary` / `.ghost`）。同一个概念两个名字，
> CSS 又不报错，后定义的静默生效。`hygiene.py` 现在会数 `.btn{` 出现的次数。
